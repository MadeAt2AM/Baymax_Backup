# OpenReply Follow-Gate Debug — Session Notes (2026-07-30)

Investigation trace for the recurring "DM not firing, no logs" symptom on the
OpenReply VPS deploy at `openreply.terrybot.top`. Captures the specific
commands that worked, the rabbit holes that wasted time, and the new
diagnostic layers surfaced this session.

## TL;DR — Run `verify-ig-token.sh` first, EVERY TIME

Before patching anything in `lib/queue/dm-worker.ts` or the webhook handler,
run the bundled script:

```bash
bash scripts/verify-ig-token.sh
```

The script now tests against `graph.instagram.com` (not `graph.facebook.com`).
If it exits with code `1` (token rejected) or code `2` (Meta App rejected),
**stop and address the auth layer** — no code patch will fix the symptom.

## The three failure layers — observed patterns

### Layer 1: Meta authentication (most common — ~70% of incidents)

**Symptoms:**
- Worker logs only show `[DM Worker] Started`, nothing else
- No new `WebhookEvent` rows from real Meta deliveries
- `OperationalEvent` empty OR contains `code: 190` in payload

**Three sub-failures this session exposed:**

#### 1a. Token invalid but decryption succeeds (code 190)

This is the classic case: `accessToken` decrypts cleanly with the current
`ENCRYPTION_KEY`, but Meta returns `{"code": 190, "message": "Cannot parse
access token"}`. The token may have been:
- Generated with a now-rotated `ENCRYPTION_KEY`
- Corrupted during a DB migration / restore
- Manually overwritten in the DB with a stale value

**Fix:** Reconnect Instagram via OAuth in the OpenReply dashboard. The OAuth
callback at `/api/instagram/callback` regenerates the token with the CURRENT
key, encrypts with `aes-256-gcm`, and stores it in `InstagramAccount.accessToken`.

#### 1b. Meta App credentials rejected (code 101)

When even the freshly regenerated token returns `code: 190`, test the App
credentials directly:

```bash
ssh dev-vps 'APP_ID=$(grep INSTAGRAM_APP_ID /srv/projects/openreply/.env | cut -d= -f2); \
  APP_SECRET=$(grep INSTAGRAM_APP_SECRET /srv/projects/openreply/.env | cut -d= -f2); \
  curl -sS -X POST "https://graph.facebook.com/v21.0/oauth/access_token" \
    -d "client_id=$APP_ID" -d "client_secret=$APP_SECRET" \
    -d "grant_type=client_credentials"'
```

**Symptoms:**
- Response: `{"error":{"code":101,"message":"Error validating application.
  Cannot get application info due to a system error."}}`
- This is NOT recoverable from the VPS. The app at Meta is in a bad state.

**Root causes (in order of frequency):**
1. App is **suspended or deleted** at Meta
2. App is in **Development mode** and the operator is not a configured tester
3. App requires **Business Verification** for the requested scopes
4. The App ID/Secret pair is **wrong** (transposed, copy-paste dropped a char)

**Resolution:** Operator must go to developers.facebook.com → their App → check
App Review status, Live mode toggle, Business Verification status, and confirm
the App ID + secrets match what `/srv/secrets/openreply.env` contains.

#### 1c. Wrong endpoint (graph.facebook.com vs graph.instagram.com) — NEW THIS SESSION

After OAuth reconnection, the freshly generated token still showed "Invalid"
when tested against `graph.facebook.com/v21.0/me`. The token was NOT actually
invalid — it was just the wrong endpoint.

**Instagram Graph API tokens are scoped to `graph.instagram.com`.** Hitting
`graph.facebook.com` with the same token always returns `code: 190` regardless
of validity. Test IG tokens against the Instagram endpoint:

```bash
# CORRECT — Instagram Graph API token validation
curl -sS "https://graph.instagram.com/v21.0/me?access_token=$TOKEN"

# Returns: {"id":"27821852394097749","username":"cyber.slide"}

# WRONG — will always return code 190 for IG tokens
curl -sS "https://graph.facebook.com/v21.0/me?access_token=$TOKEN"
# Returns: {"error":{"code":190,...}}
```

This burned ~5 tool calls in the session before the endpoint switch.

### Layer 1.5: Permission gap (NEW THIS SESSION)

After confirming token validity via `graph.instagram.com/v21.0/me`, the next
symptom was "comments exist on the post but the worker can't see them."

**Signature:** `comments_count > 0` from media endpoint, **but** `/comments`
endpoint returns `{"data": []}`.

```bash
# Media endpoint returns counts (uses instagram_business_basic — usually granted)
curl ".../me/media?fields=id,media_type,comments_count"
# → "comments_count": 3

# Comments endpoint returns empty (uses instagram_business_manage_comments)
curl ".../<POST_ID>/comments"
# → {"data": []}
```

**Root cause:** Token has metadata read scope (`instagram_business_basic`) but
NOT content read scope (`instagram_business_manage_comments`). This happens
when the operator didn't check all permission boxes on the OAuth consent
screen during Instagram reconnection, even though the OAuth scope list in
code requests all four permissions.

**Fix:** Reconnect Instagram in OpenReply settings. On the Instagram consent
screen, ensure **all** permission checkboxes are ticked BEFORE clicking
Authorize. A partial grant produces a token that can fetch counts but not
content.

### Layer 2: Webhook delivery (rare — most likely if Layers 1 & 1.5 pass)

If Layers 1 & 1.5 pass but `WebhookEvent` table is empty despite recent
comments:
- App not Live at Meta (Meta drops events silently)
- Webhook subscription missing `comments` field
- Callback URL returns non-200 on GET (`hub.verify` fails)
- `WEBHOOK_VERIFY_TOKEN` in Meta dashboard does not match `process.env.WEBHOOK_VERIFY_TOKEN`

### Layer 3: Worker logic (least common — only when Layers 1, 1.5 & 2 all pass)

Only investigate here if Layers 1 & 1.5 pass (token valid + permissions
correct) and Layer 2 shows `WebhookEvent` rows but no `DmLog` rows. The
line-407 `!== true` bug is already patched.

## Commands that actually worked this session

### Decrypt the stored token (canonical recipe)

```bash
# 1. Pull encrypted token
ssh dev-vps 'docker exec openreply-postgres-1 psql -U openreply -d openreply \
  -tA -c "SELECT \"accessToken\" FROM \"InstagramAccount\" LIMIT 1"' \
  > /tmp/enc_token.txt

# 2. Write decrypt script as base64 (avoids heredoc shell-escape disasters)
cat > /tmp/decrypt.mjs << 'EOF'
import { createDecipheriv } from "crypto";
import fs from "fs";
const enc = fs.readFileSync(process.argv[2], "utf8").trim();
const E = process.env.ENCRYPTION_KEY;
const key = Buffer.from(E, "hex");
const combined = Buffer.from(enc, "base64");
const iv = combined.subarray(0, 16);
const tag = combined.subarray(16, 32);
const ct = combined.subarray(32);
const dec = createDecipheriv("aes-256-gcm", key, iv);
dec.setAuthTag(tag);
fs.writeFileSync(process.argv[3], Buffer.concat([dec.update(ct), dec.final()]).toString("utf8"));
EOF
B64=$(base64 -w 0 /tmp/decrypt.mjs)
ssh dev-vps "echo '$B64' | base64 -d > /tmp/dec.mjs && \
  docker cp /tmp/enc_token.txt openreply-web-1:/tmp/enc_token.txt && \
  docker cp /tmp/dec.mjs openreply-web-1:/tmp/dec.mjs && \
  docker exec openreply-web-1 node /tmp/dec.mjs /tmp/enc_token.txt /tmp/plain_token.txt && \
  docker cp openreply-web-1:/tmp/plain_token.txt /tmp/plain_token.txt"

# 3. Test against Meta — use graph.instagram.com, NOT graph.facebook.com
TOKEN=$(cat /tmp/plain_token.txt)
ssh dev-vps "curl -sS 'https://graph.instagram.com/v21.0/me?access_token=$TOKEN'"
```

**Pitfall avoided:** When staging the decrypt script via `echo`, **never** use
`head -c N` to truncate it — Node will write a partial file that decodes to
truncated output and you'll chase a phantom "invalid token" diagnosis. Always
write the full script, then truncate the output AFTER `cat /tmp/plain_token.txt`
if you just want a preview.

### Test app credentials (Layer 1b probe)

```bash
ssh dev-vps 'APP_ID=$(grep INSTAGRAM_APP_ID /srv/projects/openreply/.env | cut -d= -f2); \
  APP_SECRET=$(grep INSTAGRAM_APP_SECRET /srv/projects/openreply/.env | cut -d= -f2); \
  curl -sS -X POST "https://graph.facebook.com/v21.0/oauth/access_token" \
    -d "client_id=$APP_ID" -d "client_secret=$APP_SECRET" \
    -d "grant_type=client_credentials"'
```

- `code: 101` → app is bad at Meta. Stop and escalate to operator.
- `code: 190` with both App Secret and fresh token → secret may be wrong, double-check.
- `{"access_token":"...", "token_type":"bearer"}` → App credentials valid; the
  issue is downstream.

### Detect permission gap (Layer 1.5 probe)

```bash
# 1. Get comment counts via media endpoint
curl -sS -G "https://graph.instagram.com/v21.0/<IG_USER_ID>/media" \
  --data-urlencode "access_token=$TOKEN" \
  --data-urlencode "fields=id,media_type,comments_count" \
  --data-urlencode "limit=5"

# 2. Try to fetch comments on the campaign post
curl -sS -G "https://graph.instagram.com/v21.0/<POST_ID>/comments" \
  --data-urlencode "access_token=$TOKEN" \
  --data-urlencode "fields=id,text,from,timestamp"
```

If step 1 shows `comments_count > 0` but step 2 returns empty, that's the
permission gap signature.

## Rabbit holes (do NOT pursue these)

These were attempted this session and wasted turns without progress:

1. **Patching dm-worker.ts follow-gate logic** — already correct in this
   codebase. The `sendFollowPrompt = alreadyFollows === false;` patch from
   the prior session was already applied. Re-checking and re-patching burns
   ~5-10 tool calls.

2. **Reseeding SMTP_PASSWORD** — the .env had a blank `SMTP_PASSWORD=` which
   was a real bug, but it caused a DIFFERENT failure mode (no magic-link
   emails), not silent DM drop. Fixing it didn't unblock the DM flow.

3. **Running `npx prisma migrate deploy`** — schema was already migrated. The
   `WebhookEvent` table exists. Running this again costs nothing but adds
   no signal.

4. **Restarting containers in a loop** — `docker compose restart` does NOT
   redeploy code; only `--force-recreate` does. If you've already done
   `--force-recreate`, doing it again won't change anything.

5. **Testing IG tokens against graph.facebook.com** — always returns 190 for
   valid Instagram Graph API tokens. Use graph.instagram.com.

## Diagnostic decision tree (cheat sheet)

```
"DMs not firing, no logs"
├── Run verify-ig-token.sh (tests graph.instagram.com)
│   ├── Exit 0 (token valid) ─────────────────► Go to Layer 1.5 (permission gap)
│   ├── Exit 1 (code 190) ───────────────────► Reconnect Instagram via OAuth
│   └── Exit 2 OR Layer 1b code 101 ──────────► Operator must check Meta dashboard
├── Layer 1.5: probe comments_count vs comments endpoint
│   ├── counts > 0, comments empty ─────────► Permission gap — reconnect, tick ALL boxes
│   └── counts > 0, comments visible ───────► Go to Layer 2 (webhook delivery)
└── After each fix, re-run probes to confirm
```

The `verify-ig-token.sh` script covers Layer 1a. For Layer 1b, the
"Test app credentials" snippet above is the canonical probe. For Layer 1.5,
the "Detect permission gap" snippet.

## Operator-facing actions (NOT VPS-recoverable)

The following need the operator to take action in the Meta developer dashboard:

1. **App Live mode toggle** — top right of app dashboard. Must be "Live" for
   public use; "In Development" only works for configured testers.

2. **Tester invite acceptance** — when an Instagram account is added as a
   tester, that account gets an invite via Instagram DM. The invite must be
   accepted before the OAuth flow returns valid tokens for that account.

3. **OAuth consent screen — check ALL boxes** — when reconnecting Instagram,
   the screen shows checkboxes for each permission. ALL must be ticked
   before clicking Authorize, otherwise the token comes back with limited
   scope (the "permission gap" symptom in Layer 1.5).

4. **Business Verification** — required for `instagram_business_manage_messages`
   and `instagram_business_manage_comments` scopes in production. Without it,
   the app can be Live but the messaging scopes will return 403 at runtime.
